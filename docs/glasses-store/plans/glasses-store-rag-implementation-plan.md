# 眼镜店仓储 + 账单 + RAG 咨询系统实施计划稿

> 状态：计划稿，待审阅。
> 约束：本文档仅用于规划二次开发路线，不代表已经开始实施。
> 关联 PRD：[glasses-store-rag-prd.md](../requirements/glasses-store-rag-prd.md)

## 1. 总体目标

将现有 PaiSmart 改造成眼镜实体店专用系统，形成“单店单仓仓储管理 + 店铺账单/配镜记录 + RAG 咨询问答”的一体化产品。

一期定位为中小微眼镜实体店使用，默认使用人数不超过 4 人，不引入多门店、多仓库、调拨、盘点和审核流。库存、商品、账单、客户配镜记录以 MySQL 为权威数据源；RAG 文档继续复用现有上传、解析、向量化和 Elasticsearch 检索链路。

## 2. 实施路线

### 阶段一：领域数据底座

目标：先建立眼镜店业务的核心数据模型，为后续仓储、账单和 AI 查询提供稳定数据源。

主要工作：

- 新增商品档案模型。
- 新增库存模型。
- 新增入库单和入库明细模型。
- 新增出库单和出库明细模型。
- 新增库存流水模型。
- 新增销售账单、账单商品明细、账单修改记录模型。
- 保留现有用户登录、JWT、角色体系，继续使用 `ADMIN` 和 `USER`。
- 建立默认单店单仓语义，不做多仓配置页面。

建议后端模块：

- `StoreProductService`
- `InventoryService`
- `SalesBillService`
- `StoreDashboardService`
- `SalesBillExcelService`

### 阶段二：仓储业务闭环

目标：让商品、入库、出库、库存和流水形成完整闭环。

主要工作：

- 商品管理支持 SKU、分类、品牌、型号、条码可空、采购价、零售价、安全库存、镜框/镜片扩展字段。
- 入库单支持草稿、确认入库、取消。
- 入库确认后，在同一事务中增加库存并写入库存流水。
- 出库单支持草稿、确认出库、取消。
- 出库确认后，在同一事务中扣减库存并写入库存流水。
- 出库数量不得超过当前库存，不允许库存变负。
- 已确认单据不得物理删除，后续如需冲销可二期扩展红冲。

核心接口：

- `GET /api/v1/store/products`
- `POST /api/v1/store/products`
- `PUT /api/v1/store/products/{sku}`
- `GET /api/v1/store/products/{sku}`
- `GET /api/v1/store/inventory/stocks`
- `GET /api/v1/store/inventory/low-stock`
- `POST /api/v1/store/inventory/inbound`
- `POST /api/v1/store/inventory/inbound/{id}/confirm`
- `POST /api/v1/store/inventory/inbound/{id}/cancel`
- `POST /api/v1/store/inventory/outbound`
- `POST /api/v1/store/inventory/outbound/{id}/confirm`
- `POST /api/v1/store/inventory/outbound/{id}/cancel`
- `GET /api/v1/store/inventory/ledgers`

### 阶段三：账单与客户配镜记录

目标：完成店铺账单录入、历史配镜记录保存和基础查询。

主要工作：

- 账单中保存客户姓名、必填手机号、购买日期、镜框型号、镜片型号、支付金额、支付方式、销售员、验光师、备注。
- 左右眼度数字段拆分存储：
  - `left_myopia_degree`
  - `left_astigmatism`
  - `left_axis`
  - `right_myopia_degree`
  - `right_astigmatism`
  - `right_axis`
- 页面和 AI 回答中拼接展示为 `近视度数-散光-轴位`。
- 同一客户每次配镜都生成一条新的账单/配镜记录，不覆盖历史记录。
- 账单修改时保留修改记录。
- 账单创建时可选择自动生成销售出库并扣减库存。

核心接口：

- `GET /api/v1/store/sales-bills`
- `POST /api/v1/store/sales-bills`
- `PUT /api/v1/store/sales-bills/{id}`
- `GET /api/v1/store/sales-bills/{id}`
- `GET /api/v1/store/sales-bills/customer-history?phone=...`

### 阶段四：Excel 模板与导入

目标：支持历史账单批量导入，并提供固定模板。

主要工作：

- 新增固定 Excel 模板下载。
- 新增账单 Excel 导入接口。
- 导入时校验必填手机号、日期格式、金额格式、度数字段格式。
- 导入成功的数据写入账单表，后续可被结构化查询和 AI 查询。
- 导入失败时返回行号和错误原因。
- 前端上传格式扩展为 `.pdf,.doc,.docx,.xls,.xlsx,.csv,.txt`。
- Excel 原文件仍可按现有 RAG 文档链路上传入库。

固定模板字段：

- 客户姓名
- 手机号
- 购买日期
- 左眼近视
- 左眼散光
- 左眼轴位
- 右眼近视
- 右眼散光
- 右眼轴位
- 瞳距
- 镜框型号
- 镜片型号
- 支付金额
- 支付方式
- 销售员
- 验光师
- 备注

核心接口：

- `GET /api/v1/store/sales-bills/template`
- `POST /api/v1/store/sales-bills/import`

### 阶段五：AI 结构化查询工具

目标：让 AI 能优先查询 MySQL 中的权威业务数据，再结合 RAG 文档作答。

主要工作：

- 扩展 `AgentToolRegistry`。
- 保留现有 `search_knowledge` 文档检索工具。
- 新增眼镜店专用工具：
  - `query_product`：查询商品档案和型号信息。
  - `query_inventory`：查询实时库存和低库存商品。
  - `query_stock_flow`：查询入库、出库和库存流水。
  - `query_sales_bill`：查询客户历史配镜、账单、金额和商品。
  - `query_store_stats`：查询今日/本月销售、热销商品、采购和出库统计。
- 修改 AI 提示词，让模型在库存、账单、客户配镜问题上优先调用结构化工具。
- AI 回答必须说明来源，例如“库存表”“账单记录”“文档来源#1”。

典型 AI 查询：

- “镜框 A123 还有多少库存？”
- “张三上次配镜的左右眼度数是多少？”
- “张三这次和上次相比，近视或散光有没有增长？”
- “今天卖了多少副眼镜？”
- “低于安全库存的商品有哪些？”
- “这款防蓝光镜片适合什么人？”

### 阶段六：前端专用化

目标：将前端从通用知识库产品改造成眼镜店业务系统。

主要工作：

- 新增 `frontend/src/service/api/store.ts`。
- 在 `frontend/src/typings/api.d.ts` 增加 `Api.Store` 类型。
- 新增页面：
  - `store-dashboard`
  - `product`
  - `inventory-stock`
  - `inventory-inbound`
  - `inventory-outbound`
  - `inventory-ledger`
  - `sales-bill`
- 默认首页推荐设置为仪表盘。
- 仪表盘展示今日销售额、库存预警、今日入库、今日出库、草稿单据。
- 商品、入库、出库、账单页面使用 Naive UI 表格、弹窗/抽屉表单、确认弹窗。
- 账单页面提供“下载模板”“导入账单”“查看历史配镜”操作。
- AI 助手保留现有聊天体验，但改为眼镜店场景文案和默认提示。
- 隐藏或移除通用 PaiSmart 不再需要的菜单，如充值、模型提供商、组织标签、邀请码等。

## 4. 测试计划

### 后端测试

- 商品 SKU 唯一。
- 条码可为空。
- 商品分类和状态校验。
- 入库确认后库存增加并写入流水。
- 出库确认后库存减少并写入流水。
- 库存不足时出库失败且不写流水。
- 已确认单据不能重复确认。
- 已取消单据不能确认。
- 同一手机号多次配镜生成多条账单记录。
- 账单修改生成修改记录。
- 度数字段拆分存储，展示 DTO 正确拼接。
- Excel 模板下载包含固定表头。
- Excel 导入成功。
- Excel 导入缺手机号失败。
- Excel 导入日期格式错误失败。
- Excel 导入金额格式错误失败。
- AI 工具查询库存、客户历史配镜、低库存、销售统计能返回可读文本和结构化数据。

### 前端验证

- `pnpm typecheck` 通过。
- 商品、库存、入库、出库、账单页面字段完整。
- 下载模板能得到 `.xlsx`。
- 导入错误能展示行号和错误原因。
- AI 助手能展示结构化查询结果和文档引用。

### 集成验证

- `mvn -q -DskipTests compile` 通过。
- 新增商品后可入库，库存增加。
- 出库确认后库存减少。
- 库存流水可按商品、时间、操作人查询。
- 同一客户录入两次配镜账单，历史记录显示两条。
- AI 能回答客户历史度数和度数变化问题。
- 上传 PDF/Word/Excel 文档后，AI 能通过文档来源回答商品或验光资料问题。
- 浏览器访问 `http://localhost:9527`，菜单、页面、接口响应和控制台无明显错误。

## 5. 默认取舍

- 一期只做单店单仓。
- 不做真实支付对接。
- 不做客户独立档案。
- 不做扫码枪和条码打印。
- 不做入库/出库审核流。
- 不做多门店、多仓库、调拨和盘点。
- 客户眼睛度数对登录店员开放，不做额外角色鉴权。
- 现有 RAG 上传、解析、向量化链路继续保留。
- 商品、库存、账单、客户配镜记录以 MySQL 为准。

## 6. 推荐执行顺序

11. 后端编译、前端类型检查、浏览器端到端验证。
