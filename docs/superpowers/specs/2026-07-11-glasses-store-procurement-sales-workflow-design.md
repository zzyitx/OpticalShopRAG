# 眼镜店单店进销存流程升级设计

> 日期：2026-07-11
>
> 状态：已确认
>
> 适用范围：PaiSmart 眼镜店单店进销存模块
>
> 设计依据：现有 Store 代码与数据库结构、已完成的基础测试、用户提供的同类软件操作流程

## 1. 背景与目标

PaiSmart 当前已经具备商品档案、入库、出库、SKU 汇总库存、库存流水、销售账单、客户配镜历史、经营看板和 AI 结构化查询等基础能力，但业务入口仍偏向技术验证版本。与门店实际使用流程相比，基础资料、采购验收、批次库存和销售审核之间还没有形成完整、易理解的日常操作链路。

本次升级以“小型眼镜店单店进销存”为边界，参考同类软件的成熟操作顺序，但不机械复制其多菜单和传统 ERP 交互。系统采用“经营台 + 独立模块”的组织方式：经营台负责首次配置、今日待办和风险提醒，基础资料、采购、销售、库存分别提供可直接进入的业务页面。

本次目标包括：

- 建立可维护的计量单位、两级商品类别、往来单位、默认仓库和商品档案。
- 支持“采购订单审核即入库”和“采购订单审核后再分次验收”两种采购模式。
- 将批号、生产日期、有效期贯通到采购、验收、批次库存、销售出库和库存流水。
- 销售时按 FEFO（先到期先出）自动推荐批次，并允许店员人工改选。
- 制单人可以直接执行审核确认；只有审核或验收确认才正式增减库存。
- 保留客户购买与配镜历史、AI 只读经营查询和 RAG 文档问答能力。
- 形成与最终真实页面一致、可供店员持续使用的 Markdown 操作流程手册。

## 2. 已确认业务边界

### 2.1 本期范围

- 单门店、单默认仓库。
- 商品类别固定最多两级。
- 计量单位可独立新增、停用和排序。
- 往来单位统一建档，可同时具有客户和供应商角色。
- 客户分类至少支持零售客户、批发客户；供应商角色保存厂家或供货商资料。
- 商品 SKU 默认自动生成，保存前允许管理员修改。
- 隐形眼镜不同度数、不同包装规格分别建立独立 SKU。
- 采购支持直接入库和后续验收两种模式。
- 后续验收支持分次到货，累计实收不得超过订购数量。
- 销售审核时按批次扣减库存，默认 FEFO 推荐，允许人工改选。
- 审核不要求另一名员工；同一用户在有权限时可以制单并审核。
- AI 只读查询适配新的采购、批次库存和风险数据，不允许 AI 审核单据或修改库存。

### 2.2 明确不做

- 多门店、多仓调拨和跨店库存。
- 必须由另一人完成的复核审批流。
- 多级采购审批、供应商结算和应付账款。
- 自动生成采购单、自动联系供应商或自动营销触达。
- 销售收款系统、真实支付渠道对接和财务总账。
- 任意深度商品分类树。
- AI 自动写商品、客户、采购、销售和库存数据。
- 医疗诊断、处方判断或替代验光师的确定性建议。

## 3. 当前能力与差距

当前实现与目标之间的主要差距如下：

| 领域 | 当前状态 | 本次设计 |
| --- | --- | --- |
| 商品分类 | `StoreProduct.ProductCategory` 固定枚举 | 新增可维护的一级、二级分类主数据 |
| 计量单位 | `StoreProduct.ProductUnit` 固定枚举 | 新增独立单位主数据 |
| 供应商 | 商品和入库单保存供应商文本 | 改为统一往来单位关联并保留单据快照 |
| 客户 | 客户姓名、手机号随销售账单保存 | 新增客户档案，同时继续保留账单历史快照 |
| 仓库 | 代码固定 `DEFAULT` | 新增单个默认仓库资料，业务仍限制单默认仓库 |
| 采购 | 现有入库单直接确认入库 | 新增采购订单和采购验收，支持两种入库模式 |
| 批次 | 入库明细实体已有批次字段，但创建请求和前端未传递 | 贯通采购、验收、库存、销售和流水 |
| 库存 | 仅有 SKU + 仓库汇总量 | 保留汇总库存并新增批次库存 |
| 销售 | 账单可自动出库，但没有单据审核状态和批次分配 | 草稿、审核、批次分配、确认出库一体化 |
| 页面 | Store 功能集中在单个经营台页面 | 经营台汇总，主数据和日常单据独立页面 |

2026-07-11 设计核对时，当前 MySQL 十张 `store_*` 业务表均为 0 行。实现仍必须按兼容迁移设计处理，不能以当前无数据为由编写破坏性改表逻辑。

## 4. 信息架构与页面组织

### 4.1 一级导航

- 经营台
- 采购管理
- 销售管理
- 库存管理
- 基础资料
- AI 助手

### 4.2 经营台

经营台保留当前经营概览，并新增：

- 首次配置完成度：计量单位、商品类别、往来单位、默认仓库、商品档案。
- 今日待办：待审核采购、待验收采购、待审核销售。
- 经营风险：低库存、缺货、近效期和已过期批次。
- 高频入口：新建采购、采购验收、新建销售。

首次配置完成后，配置引导折叠为“基础资料完整性”状态，不占用日常经营台主要空间。

### 4.3 独立页面

- 基础资料：计量单位、商品类别、往来单位、仓库设置、商品档案。
- 采购管理：采购订单、采购验收。
- 销售管理：销售订单、客户购买与配镜历史。
- 库存管理：SKU 汇总库存、批次库存、库存流水。

列表页统一支持编号、名称、状态和日期筛选，采用有界分页查询。点击列表记录后使用详情抽屉展示业务快照、审核信息、验收记录和库存流水；新建和编辑单据使用独立页面，避免复杂明细表格被压缩在弹窗内。

## 5. 主数据设计

### 5.1 计量单位

计量单位包含稳定编码、显示名称、启用状态、排序号和审计字段。系统初始化“盒、瓶、片、副、个”等常用单位。单位被商品引用后不得物理删除，只允许停用；停用单位不允许用于新商品，历史商品和单据继续显示原名称。

### 5.2 两级商品类别

商品类别包含稳定编码、名称、父类别、层级、启用状态、排序号和审计字段。一级类别没有父节点，二级类别必须关联一个一级类别；后端拒绝创建第三级。系统可初始化隐形眼镜、护理产品等一级分类，具体二级分类由管理员维护。

类别被商品引用后不得物理删除。停用类别不能用于新商品，但不改变历史商品和单据。

### 5.3 往来单位

往来单位作为客户和供应商的统一底层主数据，至少保存：

- 往来单位编码、名称、联系人、联系电话、地址。
- 是否客户、是否供应商。
- 客户分类：零售客户、批发客户；仅具有客户角色时生效。
- 启用状态、备注和审计字段。

页面分别提供“客户资料”和“供应商资料”入口，但两者操作同一份往来单位数据。一个厂家可以同时具有客户和供应商角色。手机号仍是查询客户购买和配镜历史的精确标识；仅凭姓名不能通过 AI 泛查多个客户的历史记录。

### 5.4 默认仓库

仓库资料保存仓库编码、仓库名称、门店名称、负责人、采购联系人、启用状态和是否默认。负责人和采购联系人从现有系统用户中选择，不另建员工档案；单据同时保存人员显示快照。

仓库表允许保留停用的历史记录，但业务层只允许一个启用的默认仓库，所有本期采购、销售和库存操作均使用该仓库，不开放多仓库存、调拨和仓间结算。

### 5.5 商品档案

商品档案关联二级或一级商品类别、计量单位和默认供应商，继续保存品牌、型号、条码、规格、颜色、材质、采购价、零售价、安全库存和状态。

SKU 由系统按稳定规则自动生成，管理员在首次保存前可以修改；保存后如已被单据引用，不允许直接修改 SKU。隐形眼镜的度数和包装规格作为商品规格的重要组成，不同可库存组合必须使用独立 SKU。

商品档案必须显式保存批次管理配置，不能通过商品类别名称猜测：

- 是否启用批次管理。
- 是否启用有效期管理。
- 生产日期是否必填。
- 近效期提醒天数；为空时使用门店默认值。

隐形眼镜、护理液等商品默认启用批次和有效期管理，镜框等普通商品可以关闭。关闭批次管理的商品仍在库存底层使用系统内部的 `NO_BATCH` 汇总批次，以便所有商品共用同一套库存守恒、锁定和流水逻辑；页面不向店员展示该内部批次。

## 6. 采购业务设计

### 6.1 采购订单公共字段

采购订单至少保存：

- 采购单号、供应商、采购员、默认仓库。
- 入库模式：`DIRECT` 直接入库、`RECEIPT` 后续验收。
- 状态、备注、创建人、审核人和时间。
- 商品 SKU、名称快照、订购数量、采购单价和金额。

采购单号由系统生成。草稿允许修改和取消；审核后不允许物理删除，只能通过后续明确设计的冲销或退货业务处理库存影响。本期不新增复杂退货结算，仅保留已有其他出入库类型的兼容能力。

### 6.2 直接入库模式

直接入库适合已经到货、无需再单独验收的临时补货。每条采购明细在审核前必须录入实际入库数量；对隐形眼镜、护理液等批次管理商品，还必须录入批号和有效期，生产日期按商品要求可选或必填。

状态流转为：

`DRAFT 草稿 → COMPLETED 已入库`，草稿也可以进入 `CANCELLED 已取消`。

审核确认在同一事务内完成：

1. 校验供应商、仓库、商品状态、数量、价格和批次信息。
2. 创建或累加批次库存。
3. 同步增加 SKU 汇总库存。
4. 写入带采购单号和批次信息的库存流水。
5. 写入审核人、审核时间并将订单置为已入库。

直接入库订单审核后禁止再创建采购验收单，避免重复入库。

### 6.3 后续验收模式

后续验收适合先下单、后到货或分批到货的采购。采购订单审核时不增加库存，状态流转为：

`DRAFT 草稿 → APPROVED 待到货 → PARTIALLY_RECEIVED 部分验收 → COMPLETED 全部完成`。草稿可以取消；已审核但尚未产生任何验收记录的订单也可以取消，已经部分验收的订单不能直接取消。

采购验收单关联采购订单和具体订购明细，保存本次实收数量、批号、生产日期、有效期、差异说明、验收人和确认时间。允许一张采购订单创建多张验收单，但累计实收数量不得超过订购数量。

每张验收单在确认时单独增加本次实收库存并写流水。确认失败时，验收状态、批次库存、汇总库存和流水必须整体回滚。

## 7. 批次库存设计

系统继续保留现有 SKU + 仓库汇总库存，作为列表和库存不足校验的快速权威入口，同时新增批次库存，至少保存：

- 仓库、商品 SKU、批号。
- 生产日期、有效期。
- 当前数量、可用数量。
- 最近入库时间、最近出库时间、状态。

同一商品、仓库、批号和有效期组合应保持唯一。每次库存事务完成后必须满足：

`SKU 汇总当前数量 = 该仓库该 SKU 所有有效批次当前数量之和`

对未启用批次管理的商品，系统使用不向页面展示的 `NO_BATCH` 内部批次参与上式计算。库存流水增加批次标识和来源单据类型，以便从销售记录追溯到具体采购或验收批次。批次已过期时禁止销售出库，并在经营台显示风险；近效期阈值优先使用商品配置，否则使用门店默认值，门店初始默认值固定为 90 天。

## 8. 销售业务设计

销售订单沿用并扩展现有 `StoreSalesBill`，避免再建立一套与客户配镜历史重复的销售主表。销售账单新增客户关联、仓库、单据状态、审核人和审核时间；账单仍保存客户姓名、手机号、商品名称、价格和配镜数据快照。

现有 Excel/CSV 历史账单导入继续保留。导入记录保存为已确认历史账单，但明确标记“未影响当前库存”；只有在新销售流程中审核确认的账单才写批次分配并扣减库存，避免导入多年旧账时误扣当前库存。

销售流程为：

1. 选择已有客户，或在销售页面弹窗快速新增零售/批发客户。
2. 选择商品和销售数量。
3. 系统按有效期升序、入库时间升序给出 FEFO 批次分配方案。
4. 店员可以展开批次分配并人工改选，但不能选择过期、停用或库存不足批次。
5. 保存草稿；草稿不占用、不扣减库存。
6. 审核时重新校验批次可用量，避免草稿期间库存变化导致超卖。
7. 审核事务内扣减批次库存、同步扣减 SKU 汇总库存、写库存流水，并保存客户购买与配镜历史。

状态流转为：

`DRAFT 草稿 → CONFIRMED 已出库`，未审核草稿可以进入 `CANCELLED 已取消`。

同一审核请求重复提交时必须返回已有结果，不得重复扣库存。库存不足、批次过期、商品停用或客户停用时，审核被拒绝，整张销售单不产生部分库存变更。

## 9. 权限、审计与隐私

在现有权限体系中拆分以下权限：

- 基础资料查看与维护。
- 采购查看、制单、审核、验收。
- 销售查看、制单、审核。
- 库存与流水查看。

同一用户可以同时拥有制单和审核权限。前端根据权限隐藏或禁用按钮，后端接口必须独立校验权限，不能只依赖页面控制。

主数据、采购、验收、销售和库存流水均记录创建人、修改人、审核人及对应时间。已审核单据保留业务快照，档案后续改名不改写历史。

客户历史查询继续要求 `customerPhone` 或 `billNo`，不允许仅凭客户姓名返回多人的配镜和购买记录。列表和日志中的手机号按权限决定是否脱敏显示。

## 10. AI 与 RAG 设计

AI 助手保持只读，继续以 MySQL 结构化数据作为库存、金额、采购、销售和批次事实来源。可扩展或适配的只读问题包括：

- 哪些采购订单仍待验收。
- 某商品各批次库存和最近有效期。
- 未来 90 天内有哪些近效期商品。
- 哪些商品低于安全库存。
- 某客户按手机号查询的购买与配镜历史。

AI 不执行采购审核、验收确认、销售审核、批次改选或库存调整。商品说明书、资质、售后政策等内容继续从 RAG 文档获取并保留引用；实时库存、金额和单据状态不得从文档推断。

## 11. 页面交互要求

- 列表采用分页和条件查询，禁止默认整表加载。
- 商品、客户、供应商和批次选择器支持编码、名称、手机号或型号搜索。
- 商品和往来单位支持在业务表单内弹窗快速新增，保存后自动回填当前表单。
- 采购验收清晰展示订购数量、累计已收、本次实收和剩余未收。
- 销售页面默认折叠 FEFO 批次分配，存在多个批次、近效期或手工修改时展开提示。
- 金额、数量和剩余量由系统实时计算，后端重新计算并校验，不能信任前端传入合计值。
- 审核或验收确认前显示库存影响摘要并要求二次确认。
- 业务错误返回稳定错误码和中文提示，页面保留用户已输入内容，不因校验失败清空表单。
- `frontend/src/views/store/index.vue` 不继续堆叠所有功能；按经营台、基础资料、采购、销售和库存拆分为职责清晰的页面与组件。

## 12. 异常处理与一致性规则

必须阻断以下情况：

- 创建第三级商品类别。
- 重复的单位、类别、往来单位或商品编码。
- 使用停用的单位、类别、往来单位、仓库或商品创建新单据。
- 对启用批次或有效期管理的商品缺少其配置要求的批号、生产日期或有效期。
- 验收数量为零、负数或累计超过订购数量。
- 销售选择过期批次或批次库存不足。
- 已审核单据再次产生库存影响。
- 物理删除已被商品或单据引用的主数据。

采购入库、验收入库和销售出库必须使用数据库事务与必要的行级锁。任一明细失败时整单回滚，不能出现单据已确认但库存未完整更新，或批次库存和 SKU 汇总库存不一致。

## 13. 兼容迁移策略

现有项目依赖 Hibernate `ddl-auto=update`，没有 Flyway 或 Liquibase。涉及主数据和批次库存的结构变化不能只依赖自动推断完成破坏性迁移。

迁移采用以下顺序：

1. 新增主数据表、批次库存表、采购订单/验收表和必要的可空关联字段。
2. 初始化常用单位、一级类别、默认二级类别、默认仓库等基础数据。
3. 将现有商品枚举值、供应商文本和 `DEFAULT` 仓库回填到新主数据关联。
4. 新代码在兼容期优先读新关联，缺失时回退旧字段；写入时保持必要快照。
5. 通过数据核验 SQL 确认无孤立记录、库存守恒和单据关联完整。
6. 只有在独立迁移和回滚验证完成后，才收紧非空约束；本期不直接删除旧字段。

所有新表和字段必须包含清楚的数据库注释；所有持久化实体属性必须包含业务含义注释。

## 14. 分阶段实施

本次升级拆成四个可独立验收的阶段：

### 阶段 1：基础资料

交付计量单位、两级商品类别、往来单位、默认仓库、商品自动编号和商品档案关联。完成后可以独立维护全部基础资料，不改变现有库存数量。

### 阶段 2：采购与批次库存

交付双入库模式、采购订单、采购验收、批次库存、汇总库存同步和批次流水。完成后可以独立走通直接入库与分次验收两条采购旅程。

### 阶段 3：销售与经营台

交付客户选择与快速新增、销售草稿/审核、FEFO 批次推荐、批次出库、经营台待办与风险提醒，以及 AI 只读查询适配。

### 阶段 4：运行态验收与操作手册

在真实前后端运行态完成业务页面、网络响应、MySQL 数据、库存守恒和 AI 查询验证。根据最终真实菜单和页面截图编写 Markdown 操作流程手册。

四个阶段分别形成实施计划和验收记录。前一阶段的数据模型和核心回归通过后，再进入下一阶段，避免把主数据、库存和销售风险集中到一次大提交中。

- 审核失败后保留用户输入并显示明确原因。
- 列表筛选和分页请求与后端响应一致。

### 15.3 运行态验收

按照仓库约定复用 IDEA 后端热部署和已有前端开发服务器。每个阶段至少验证：

1. 最新后端代码已编译并加载。
2. 浏览器真实页面可以完成自然业务路径。
3. 网络请求路径、参数、响应体和错误码正确。
4. MySQL 中主数据、单据、批次库存、汇总库存和流水一致。
5. 涉及 AI 时，工具事件、结构化来源和最终回答一致。

核心数量断言为：

- 采购确认或验收确认后的库存增加量等于本次实收量。
- 销售确认后的库存减少量等于审核时批次分配量。
- 每条库存流水满足“变动前数量 + 变动数量 = 变动后数量”。
- 每个 SKU 的汇总库存等于其全部有效批次库存之和。
