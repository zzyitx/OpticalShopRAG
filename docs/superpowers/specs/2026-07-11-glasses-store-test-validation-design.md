>
> 状态：已确认

> 原始样例：`测试用例/26.6.26（补单）视倍舒半.pdf`、`测试用例/眼睛店客户数据用例.xlsx`

## 1. 背景与目标

本次工作以眼镜店提供的补货单和客户配镜历史为事实样例，构建可重复执行、可独立复算、可追溯证据的完整验收包，并在本地真实运行环境中完成业务接口、浏览器、MySQL、AI 结构化查询和 RAG 问答的端到端验证。

目标包括：

- 验证商品、入库、出库、库存、流水、销售账单、客户历史和仪表盘的业务闭环。
- 验证 Excel 历史账单导入、异常数据处理和账单变更审计。
- 验证五类 AI 结构化查询工具、RAG 文档问答及混合查询的来源优先级。
- 验证业务接口、MySQL、页面和 AI 回答的数据一致性。
- 识别真实门店数据与当前模型、接口之间的能力缺口。
- 形成可供后续回归测试和项目演示复用的脱敏测试资产。

本次只报告发现的缺陷，不修改现有业务代码。执行完成后不保留测试数据。

## 2. 原始样例事实

### 2.1 补货单

PDF 为一张隐形眼镜随货同行单，包含 41 条批次明细，覆盖 28 个光度，商品数量合计 56 片。每个光度按批次汇总后的数量均为 2 片。

可验证字段包括：

- 商品名称、光度、规格或型号。
- 批号、失效日期、注册证号。
- 生产企业、生产许可证号。
- 每批数量、复合结论、供应商、收货信息和制单日期。

补货单既用于构造商品和入库测试数据，也作为 RAG 文档上传，验证批号、失效日期和资质信息问答。

### 2.2 客户配镜历史

Excel 包含 17 条历史记录和两位客户，日期范围从 2011 年至 2026 年。样例同时包含正常数据和真实脏数据：

- 多年重复配镜历史。
- 一条完全重复记录。
- 大量缺失手机号和部分缺失性别。
- `女`、`女生`、`男`、`男孩` 等不一致文本。
- 复合度数、仅散光加轴位、单一近视度数等多种写法。
- 瞳距随年份变化。
- `ADD+75` 和数字 `1` 等业务含义暂不确定的数据。
- 一处疑似金额或附加字段的孤立数字。

已确认的度数转换规则：

- `-250-75*135` 表示近视 250 度、散光 75 度、轴位 135，落库值分别为 `-2.50`、`-0.75`、`135`。
- `-75*170` 表示无近视、散光 75 度、轴位 170，落库值分别为 `0.00`、`-0.75`、`170`。
- `ADD+75` 和同列数字 `1` 保留原始值并标记为“业务含义待门店确认”，不生成确定性断言。当前账单模型没有 `ADD` 字段，该问题同时记入能力缺口。

## 3. 数据安全与处理原则

- 原始 PDF 和 Excel 保持只读，不覆盖、不重命名、不写回。
- 所有衍生数据替换真实姓名、手机号、门店地址、联系人和联系电话。
- 度数、日期跨度、数量、批次关系、重复、缺失和异常形态保持不变。
- 同一客户使用稳定的脱敏手机号；同名不同客户使用不同手机号。
- 无法确定业务含义的字段保留原文并进入人工复核列，不静默猜测。
- 测试数据使用唯一前缀和批次标识，确保可追踪和可定向清理。
- 证据文件中的 Token、Cookie、手机号和其他身份信息必须脱敏。

## 5. 测试数据分层

### 5.1 样例转录层

逐行转录脱敏后的 41 条补货批次和 17 条配镜历史，保留原始字段、原始值、来源文件、页码或行号及人工复核标记。该层不直接导入业务系统。

### 5.2 可执行数据层

- 为 28 个光度分别创建隐形眼镜 SKU。
- 将可确认的度数拆分为近视、散光、轴位三个字段。
- 为正常客户历史补充稳定的脱敏测试手机号。
- 按系统下载的固定账单模板组织历史导入数据。
- 增加少量近期控制账单和镜框、镜片商品，用于验证自动出库、今日统计、低库存和 AI 经营查询。

### 5.3 异常数据层

异常集至少覆盖：缺失手机号、错误表头、列数错误、重复行、非法日期、非法轴位、零数量、负数量、负金额、无效枚举、重复 SKU、停用商品和库存不足。

## 6. 数据装载与验证流程

1. 记录执行前 Git、端口、数据库和知识库基线。
2. 通过业务页面或 API 创建 28 个光度 SKU 及配套控制商品。
3. 按 PDF 原始批次创建 41 条入库明细并确认入库。
4. 核对总库存为 56、每个光度库存为 2，并核对 41 条库存流水的数量守恒。
5. 从转录层生成脱敏补货单 PDF，确认不含真实身份信息后上传知识库，等待解析和索引完成。
6. 使用系统固定模板导入标准化客户历史；使用异常文件验证校验和失败计数。
7. 通过 API 创建包含商品明细和自动出库的近期控制账单。
8. 执行页面、接口、MySQL、AI 结构化查询和 RAG 问答核验。
9. 汇总证据和结果后，定向清理本次创建的数据并复核基线。

除验收结束后的定向清理外，MySQL 只作为权威数据核对来源，不用于绕过业务接口写入测试数据。

## 8. 核心业务旅程

### 8.1 补货旅程

PDF 转录 → 创建 28 个光度 SKU → 创建 41 条入库明细 → 确认入库 → 总库存 56 → 每个光度库存 2 → AI 查询实时库存 → RAG 查询批号和失效日期。

### 8.2 客户旅程

导入历史配镜记录 → 按手机号查询客户历史 → 对比历年度数 → 创建近期销售账单并自动出库 → 核对库存和流水 → AI 查询客户变化和经营统计。

## 9. 核心断言与来源优先级

- 每条流水必须满足“变动前数量 + 变动数量 = 变动后数量”。
- 业务接口、MySQL、页面和 AI 回答中的库存、账单数、金额和客户历史必须一致。
- 库存、账单、金额和销量以 MySQL 结构化数据为准。
- 批号、失效日期、注册证号、说明书和政策以 RAG 文档为依据，并保留引用。
- 混合问题必须同时说明结构化业务来源和文档来源，不能用 PDF 中的历史数量冒充实时库存。
- 客户历史优先使用手机号精确查询；仅凭姓名泛查应拒绝或要求补充手机号。
- 无数据、参数错误、权限不足、工具失败或文档未索引完成时必须明确说明，不得编造。
- 原始 Excel 整表直接导入失败属于预期结果；只有转换后的固定模板用于正向导入验收。

## 10. 结果状态与缺陷边界

结果状态统一使用：

- `通过`：实际结果满足明确断言。
- `失败`：当前已实现能力不满足需求或断言。
- `阻断`：环境、权限或依赖导致用例无法执行。
- `暂不支持`：当前代码或接口明确没有该能力。
- `数据风险`：来源含义不确定或转换存在业务确认要求。

当前入库实体虽有批号和失效日期字段，但入库请求未接收这些字段。该问题按“结构化能力缺口”记录，同时使用 RAG 验证文档事实查询，不与当前已实现能力的失败混为一谈。

发现缺陷时只记录严重级别、复现步骤、预期与实际结果、页面或接口证据、MySQL 证据、影响范围和修复建议，不修改业务代码。

## 11. 运行、证据与清理

### 11.1 运行原则

- 优先复用 IDEA 后端热部署和已有前端开发服务器。
- 当前探测到 `8081` 和 `9527` 均未监听，执行阶段需先按仓库约定恢复真实运行态。
- 后端 Java 变更验证优先使用 `mvn -q -DskipTests compile`；本次不修改 Java 代码。
- UI 和 AI 用例必须在真实浏览器中检查网络请求、响应体和控制台。
- 数据相关结论必须同时检查 MySQL；RAG 相关结论还需检查文件、索引和引用链路。

### 11.2 基线验证

执行前后记录以下基线：

- Store 业务表行数及最大主键。
- 测试 SKU、测试手机号和测试文件名是否存在。
- 前端、后端、MySQL、Redis、Elasticsearch、Kafka 和 MinIO 可用性。
- Git 工作区状态，确保不覆盖用户已有修改。

### 11.3 定向清理

- 草稿单据优先通过业务接口取消。
- 已确认单据和商品因当前系统缺少删除入口，只按执行期间捕获的记录 ID、测试 SKU 和脱敏手机号，在事务内按外键依赖顺序定向清理。
- 清理前验证目标集合全部属于本次测试；发现非测试记录立即停止。
- RAG 测试文件通过系统文件删除能力清理，并复核 MySQL 文件记录、Elasticsearch 片段和 MinIO 对象。
- 清理后重新执行基线 SQL，确认没有测试业务数据和测试知识文件残留。
- 清理失败按阻断项处理，不宣称验收完成。

## 12. 完成标准

- 约 116 条用例均有明确状态和可定位证据。
- 两条核心业务旅程均形成端到端结论。

- 已实现功能、能力缺口、环境阻断和数据风险分别统计。
